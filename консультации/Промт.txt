Проблема «тупняка» ИИ-агентов (Cursor, Copilot, Devin и др.) на «биг пикче» (big picture) очень распространена. Когда вы просите ИИ «прикрутить одно к другому», он пытается сгенерировать слишком много кода сразу, теряет контекст, начинает галлюцинировать или выдает поверхностные решения.
Чтобы ИИ справился, нужно декомпозировать задачу и давать ему промты по принципу: Роль → Контекст → Конкретная задача → Ограничения → Формат вывода.
Вот пошаговая стратегия и готовые промты, чтобы заставить ИИ качественно интегрировать nlb-studio6 с Astro + Tina CMS.
⚠️ Подготовка перед промтами (Критически важно!)
Прежде чем копировать промты, сделайте следующее в вашем ИИ-агенте (например, в Cursor):
Добавьте оба репозитория (nlb-studio6 и новый astro-tina) в рабочее пространство (Workspace).
Откройте файлы, которые ИИ должен видеть (например, package.json из nlb-studio6 и структуру папок).
Если используете Cursor, создайте файл .cursorrules в корне и напишите там: "Ты — Senior Fullstack Architect. Всегда сначала анализируй контекст, задавай уточняющие вопросы, если архитектура неоднозначна, и пиши код пошагово, не пытаясь сделать всё за один раз."
Шаг 1: Заставить ИИ спроектировать «Мост» (Архитектура)
Не давайте ИИ писать код, пока он не поймет, как данные будут перетекать.
Промт 1:
Роль: Ты Senior Frontend Architect, специализирующийся на Astro, Tina CMS и Next.js.
Контекст: У нас есть существующий проект приложения/сайта nlb-studio6 (стек: [укажите здесь, например, Next.js/React]). Мы хотим вынести управление контентом лендинга (тексты, цены, блоки) в Astro + Tina CMS, чтобы маркетологи могли менять его визуально, не трогая основной код приложения.
Задача: Предложи 2 конкретных архитектурных варианта интеграции:
Astro как отдельный репозиторий лендинга, который забирает данные из nlb-studio6 по API.
Monorepo (Turborepo), где Astro (с Tina) и nlb-studio6 делят общую папку /content или /schema.
Ограничения: Не пиши код реализации пока. Только сравнение плюсов/минусов, сложность настройки и твоя рекомендация для проекта среднего размера.
Формат: Маркированный список, четко и по делу.
Шаг 2: Создание схемы данных (Контракт)
Как только ИИ предложил вариант (скорее всего, он посоветует Monorepo или общую папку с контентом, если это один проект), заставьте его описать структуру данных.
Промт 2:
Контекст: Мы выбрали вариант [укажите вариант, например, "Astro + Tina CMS управляет контентом, а nlb-studio6 рендерит это, либо мы мигрируем лендинг nlb-studio6 на Astro"].
Задача: Напиши полный файл tina/schema.ts для Tina CMS.
Требования к схеме:
Коллекция landing_page с полями: hero_title, hero_subtitle, cta_button_text, features (массив объектов с иконкой, заголовком и описанием), pricing (массив тарифов).
Используй строгую типизацию TypeScript.
Добавь комментарии к каждому полю, объясняющие, как это поле будет использоваться во фронтенде nlb-studio6.
Ограничения: Пиши только код файла schema.ts и краткое пояснение, где он должен лежать в структуре Astro. Не генерируй остальные файлы.
Шаг 3: Настройка Astro для чтения данных из Tina
Теперь, когда схема есть, ИИ должен показать, как Astro ее читает.
Промт 3:
Контекст: Схема Tina CMS (schema.ts) создана. Мы работаем в репозитории Astro.
Задача: Напиши код для Astro-компонента HeroSection.astro и страницы src/pages/index.astro.
Требования:
Используй локальный GraphQL-клиент Tina (import { client } from 'tina-graphql-gateway-cli' или актуальный для Astro способ получения данных из .tina/__generated__).
Сделай типизированный запрос (Typed Document Node) к данным лендинга.
Рендеринг должен быть статическим (SSG) на этапе сборки Astro.
Ограничения: Используй Tailwind CSS для стилизации. Не добавляй сложную логику, только чистый вывод данных из Tina.
Шаг 4: Интеграция с существующим nlb-studio6 (Самый сложный шаг)
Здесь ИИ чаще всего «тупит». Нужно дать ему жесткие рамки.

Промт 4А:
Контекст: У нас есть рабочая Tina CMS в папке /astro-cms. Наш основной апп nlb-studio6 должен отображать эти данные.
Задача: Напиши скрипт build-content.ts для nlb-studio6, который:
Читает JSON-файлы, сгенерированные Tina CMS из папки .tina/__generated__ (или напрямую из .tina/content).
Экспортирует эти данные как типизированный JSON-объект, который можно импортировать в компоненты Next.js/React проекта nlb-studio6.

Промт 4Б:
Контекст: Мы переносим публичный лендинг из nlb-studio6 в новый репозиторий Astro + Tina CMS. Старый nlb-studio6 будет жить на маршруте /app или на поддомене.
Задача:
Проанализируй структуру компонента лендинга в nlb-studio6 (я сейчас открою тебе файл [укажите файл, например, src/app/page.tsx]).
Перепиши этот компонент на HeroSection.astro, используя данные из схемы Tina CMS, которую мы создали ранее.
Сохрани визуальный стиль (Tailwind классы), но адаптируй логику под статический рендеринг Astro.
Ограничения: Не используй React-хуки (useState, useEffect). Только пропсы и статические данные из Tina.
💡 Лайфхаки, чтобы ИИ не «тупил»:
Правило одного файла: Никогда не просите ИИ «переделать весь сайт». Просите: «Напиши только файл src/components/TinaHero.astro на основе этой схемы».
Скармливайте контекст вручную: Если ИИ не видит файл, скопируйте его содержимое в промт: «Вот текущий код моего компонента из nlb-studio6: [вставить код]. Адаптируй его под Astro + Tina».
Используйте режим «План перед кодом»: Добавьте в конец любого промта фразу: "Прежде чем писать код, кратко опиши план действий из 3-4 шагов и дождись моего подтверждения 'OK'". Это резко снижает количество галлюцинаций.
Для Tina CMS специфика: Напоминайте ИИ: "Помни, что Tina CMS работает в режиме local development через tinacms dev, а данные хранятся в Markdown/JSON в репозитории. Не предлагай решения с PostgreSQL или внешними API, если я явно об этом не попросил".
Попробуйте начать с Промта 1, дождитесь ответа, затем дайте Промт 2. Такой пошаговый контроль заставит ИИ работать как опытный разработчик, а не как генератор случайного кода. Если на каком-то шаге ИИ выдаст ошибку, просто скопируйте текст ошибки обратно в чат с припиской: "Исправь этот код, учитывая данную ошибку. Не меняй остальную логику".
