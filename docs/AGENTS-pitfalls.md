# Pitfall'ы (грабли, реально пойманные при порте)

> Каждый пункт: **симптом → корневая причина → фикс → урок.** Не выдуманные — всё из этого проекта.

## 1. `ssr.noExternal: ['react-slick']` чинит build и ломает dev

**Симптом.** `astro build` — `Complete!`. `astro dev` — падение ровно 30 страниц с `exports is not defined` в `eval at instantiateModule` (vite). `/services` и все динамические страницы не грузятся, `/` и `/all-events` работают.

**Причина.** Пакет CJS, импортируемый ESM-графом. `ssr.noExternal` заставил Vite обработать его как ESM — и в dev он попал в `eval`-контекст без `exports`. Странность: дев-сервер продолжал отдавать старый граф, собранный **до** включения флага, поэтому ошибка выглядела недетерминированной.

**Фикс.** Убрать `ssr.noExternal`. Interop сделать точечно в `src/site/lib/slider.ts` (нормализация default/named export). Работает и в dev, и в build.

**Урок.** Один и тот же флаг нельзя чинить двумя разными способами: `noExternal` чинит build и ломает dev — это **не** взаимозаменяемые настройки. Если после правки конфига поведение «плавает» — сначала добейся чистого рестарта, потом делай выводы.

## 2. Границы Astro-островов: React-контекст через них не проходит

**Симптом.** `useParams()` внутри страницы возвращает `{}` при корректном `params`, переданном из `.astro`.

**Причина.** Astro гидратирует **каждый остров отдельным React-root**. Контекст, созданный в компоненте-обёртке, не виден странице, если она в другом острове.

**Фикс.** `src/site/lib/with-router.tsx` — HOC `withRouter(Page)`, который сам оборачивает страницу в `SiteRouterProvider`. Обёртка должна быть **внутри** того же острова.

**Урок.** Не пытаться «обернуть остров в провайдер» из `.astro`. Провайдер обязан быть частью экспортируемого компонента.

## 3. Astro не гидратирует компонент, полученный вызовом функции

**Симптом.** `<Page client:load />` без ошибок, но интерактив мёртвый.

**Причина.** `<Page client:load />` — это JSX-вызов, а Astro видит только статический импорт. Если компонент получен как `withRouter(Page)` прямо в шаблоне, гидратация не подключается.

**Фикс.** Тонкие модули-обёртки в `src/site/routes/*.tsx`: `export default withRouter(Page)`. В `.astro` — только статический импорт этого модуля.

**Урок.** Правило: `client:*` работает только на статически импортированном компоненте.

## 4. `withRouter` проглатывал пропсы страницы

**Симптом.** Данные из хранилища (`items`) передавались в `<Page items={items} />`, но страница их не видела — показывала дефолт.

**Причина.** `function WithRouter({ params = {}, search = '' })` принимал только `RouteProps` и рендерил `<Component />` без `...rest`.

**Фикс.** `function WithRouter({ params = {}, search = '', ...rest })` → `<Component {...(rest as P)} />`.

**Урок.** Обёртка, которая не пробрасывает пропсы, молча ломает передачу данных. Обёртка — тоже контракт.

## 5. `Number(null) === 0`: запрос без `id` проходил валидацию

**Симптом.** `DELETE /api/admin/posts` без `?id=` отдавал **404 «Запись не найдена»** вместо **400 «Не передан id»**.

**Причина.** `Number(url.searchParams.get('id'))` — `get()` вернул `null`, `Number(null)` === `0`, `Number.isFinite(0)` === `true`. Валидация прошла, дальше `remove(0)` ничего не нашёл → 404.

**Фикс.** Проверять отсутствие параметра **до** приведения: `if (raw === null || raw.trim() === '') return fail(..., 400)`.

**Урок.** `Number.isFinite` **не** ловит отсутствие значения — только нечисловую строку. Проверка «параметр пришёл?» и проверка «параметр корректен?» — это две разные проверки.

## 6. `static` несовместим с админкой, которая должна быть видна сразу

**Симптом.** Админка сохраняет, а сайт не меняется до пересборки.

**Причина.** При `output: 'static'` страницы читают контент **на этапе сборки**. Админка пишет в рантайме — в пререндеренный HTML это попасть не может в принципе.

**Фикс.** `output: 'hybrid'` + `@astrojs/node`. Контентные страницы помечены `export const prerender = false` и читают `src/lib/content.ts` на каждый запрос. Маркетинговые страницы остались статикой.

**Урок.** Требование «правка в админке видна на сайте без пересборки» **несовместимо** со статической генерацией. Это не баг конфига — это архитектурный выбор, который надо сделать явно.

## 7. Парсинг исходника `new Function` спотыкается о тип-аннотацию

**Симптом.** Сид-скрипт записал 14 строк вместо 19 — демо-записи админки потерялись.

**Причина.** `mockSrc.indexOf('[', mockStart)` нашёл **`[`** в аннотации типа `WPPost[]`, а не `[` массива. Дальше парсер считал скобки и завершился на `-1`, вернул не массив.

**Фикс.** Искать `'= ['` после имени константы, а не просто `'['`.

**Урок.** Сид данных должен парсить **ровно тот литерал**, который рендерится страницей, иначе «перенос контента в хранилище» тихо меняет вид сайта.

## 8. Классы Tailwind v4 не существуют в v3 — и это тихо

**Симптом.** Иконка кнопки не по размеру, скругление «не такое», контур фокуса не виден. Стили не падают, ошибок нет.

**Причина.** В исходнике — v4-синтаксис: `size-9` (→ `h-9 w-9`), `size-4` (→ `h-4 w-4`), `rounded-xs` (→ `rounded-sm`), `outline-hidden` (→ `outline-none`). В v3 таких утилит нет, элемент просто теряет размер/радиус.

**Фикс.** Механическая замена при порте. Список — в коммите, чтобы ревью видел, что менялось только это.

**Урок.** Отсутствие CSS-класса — **не ошибка сборки**. Визуальная регрессия может уехать незамеченной. Проверять computed styles в браузере, а не только HTTP 200.

## 9. `slick.css`: кастомные точки и стрелки потерялись

**Симптом.** Слайдер на `/services` выглядит «по умолчанию»: стандартные точки вместо вытянутых градиентных, стрелки видимы.

**Причина.** `slick.css` был частично перезаписан, плюс в `SiteLayout.astro` остался **дублирующий** импорт вендорного `slick.css`, который перебивал кастомизацию.

**Фикс.** Восстановить `slick.css` **побайтово** из исходника, убрать дублирующий импорт из layout.

**Проверка (обязательная после правки CSS слайдера).** Активная точка: `28×10px`, `radius 6px`, `linear-gradient(to right, rgb(37,99,235), rgb(147,51,234))`. Простая точка: `10×10px`, `#e5e7eb`. Стрелки: `display: none` при ширине 800px.

**Урок.** Два источника одного CSS = непредсказуемый каскад. И «страница отдаёт 200» ничего не говорит о том, что слайдер выглядит правильно.

## 10. Страница новости молча теряла `content`

**Симптом.** Публикация из админки создаётся, появляется на `/all-news`, открывается по `/news/<id>` — но на странице только короткое описание, полного текста нет.

**Причина.** `toPublicNews()` не отдавал `content`, а `news-detail.tsx` рендерил `item.description`. Поле сохранялось в хранилище, но не доходило до рендера.

**Фикс.** Добавить `body?: string` в `PublicNews`, маппить `body: item.content || item.excerpt`, рендерить `item.body || item.description`. У сидированных новостей `content === description`, поэтому вид не изменился.

**Урок.** «Поле сохранилось» ≠ «поле показывается». Проверять путь **запись → чтение → рендер** целиком. И при добавлении поля в публичную модель — проверять, что это не меняет вид для старых данных.

## 11. ISO-дата из админки показывалась пользователю как `2026-10-03`

**Симптом.** Новость из панели на сайте с датой `2026-10-03` вместо `3 октября 2026`.

**Причина.** Сидированные записи хранят дату готовой строкой (`15 июня 2024`), а `upsert` проставляет ISO (`new Date().toISOString().slice(0, 10)`).

**Фикс.** `formatDate()` в `src/lib/content.ts`: если значение матчит `^\d{4}-\d{2}-\d{2}$` — привести к русскому формату, иначе вернуть как есть (чтобы не менять вид старых записей).

**Урок.** У данных, созданных человеком, и у данных, созданных машиной, **разные форматы** в одном поле. Нормализация на границе рендера безопаснее, чем миграция данных.

## 12. Черновик был невидим, но отдавал 200

**Симптом.** Черновик не появлялся на `/all-news`, но `/news/<id>` отдавал 200 с пустой страницей.

**Причина.** Фильтр `visible` стоял в списке, а страница детали брала `id` без проверки статуса.

**Фикс.** Страница детали читает только `readPublished()` и при отсутствии записи ставит `Astro.response.status = 404` плюс рендерит «Новость не найдена».

**Урок.** Скрытие в списке **не** равно 404. Для несуществующего и неопубликованного должен быть один и тот же честный ответ.

## 13. Ссылки на несуществующие роуты: 8 битых из коробки

**Симптом.** 6 ссылок вида `/news/N` и 2 ссылки на полиграфию вели в никуда.

**Причина.** В `nlb-studio6-main/src/app/routes.tsx` роута `/news/:id` **нет вообще**, хотя ссылки на него есть. Для полиграфии `getStaticPaths()` перечислял только ключи `printingServiceDetails`, а каталог ссылался ещё и на `document-printing` и `scanning`.

**Фикс.** (а) Создать `/news/[id]` из `newsItems`, экспортируемого `all-news-page.tsx` — данные те же, заголовки не могут разойтись. (б) `getStaticPaths()` = **объединение** ключей деталей и id каталога. (в) Добавить защиту «неизвестный id → 404», а не белый экран.

**Урок.** `getStaticPaths()` строит список страниц из данных. Если сайт ссылается на id из **другого** массива — будет битая ссылка. Сверять id всех источников, а не только тех, что перечислены в `getStaticPaths`.

## 14. `astro-island: 0` на `/admin/**` — не дефект

**Симптом.** Смоук показывает `astro-island: 0` на всех админ-страницах, «ничего не гидратируется».

**Причина.** Админка — серверный Astro + vanilla JS в `<script>`. React-островов там нет по замыслу.

**Фикс.** Ничего. Различать публичный сайт (1 остров на страницу) и админку (0 островов) в проверках.

**Урок.** Метрика «0 островов» дефект на сайте и норма на админке. Проверка должна знать, что измеряет.

## 15. Пять внешних картинок отдают 404 (не наша поломка)

**Симптом.** На главной грузятся 6 картинок из 8. На `/services` — часть.

**Причина.** Сами URL мёртвые: `photo-1556388250-b4c74c57376c`, `photo-1581094794329-c8592a1881d8`, `photo-1583463699313-290071c67f56`, `photo-1516131206008-dd2c85b3b1dd` + логотип Wikimedia. Проверено прямым запросом: Unsplash отвечает **404**, остальные его URL отвечают 200 — то есть это не блокировка сети.

**Фикс.** Не трогать. Ссылки **побайтово идентичны** исходнику (`nlb-studio6-main\src\app\components\news.tsx:18,25` и т.д.), то есть это дефект оригинала, а не регрессия порта.

**Урок.** Прежде чем «чинить картинку», проверь (1) мёртвый ли URL апстримом, (2) совпадает ли он с исходником. Иначе рискуешь «улучшить» оригинал и сломать требование паритета.

## 16. Конфиг, пойманный Astro в момент редактирования

**Симптом.** `ReferenceError: node is not defined`, затем `Continuing with previous valid configuration`.

**Причина.** Импорт `@astrojs/node` и `adapter: node(...)` добавлялись **двумя отдельными правками**. Между ними Astro перезагрузил конфиг и увидел `adapter` без импорта.

**Фикс.** Добавлять импорт и использование одной правкой; после правки конфига — рестарт.

**Урок.** Транзиентная ошибка конфига после правки — не «сломанный проект». Перечитай файл перед выводами.

## 17. Дев-сервер отдаёт старый граф после смены конфига

**Симптом.** Часть страниц работает, часть падает с ошибкой импорта; в логе — ошибки, которых в коде нет.

**Причина.** Процесс на порту 4321 жил с прошлым набором флагов. Правил конфиг — процесс не перезапустился.

**Фикс.** Убить процесс на порту и стартовать заново: `Get-NetTCPConnection -LocalPort 4321 -State Listen | Stop-Process -Force`.

**Урок.** Прежде чем искать баг в коде после правки конфига — перезапусти сервер. Иначе «невозможные» ошибки отправляют в ложный след.

## 18. Powershell: `$var` и кавычки ломают inline-команды

**Симптом.** `ParserError: ExpectedValueExpression` на `$LASTEXITCODE`; `NotSpecified: ...:String` вместо вывода git.

**Причина.** Вложенные `powershell -Command "..."` съедают `$`. Кавычки Node `-e "..."` конфликтуют с кавычками PowerShell.

**Фикс.** Скрипты писать файлами (`*.mjs`) и запускать `node файл.mjs`. Exit code получать через `spawnSync` в `.cjs`, а не через `$LASTEXITCODE`.

**Урок.** На этой машине inline-команды PowerShell — источник ложных ошибок. Длинная логика = файл.

## 19. `| Select-Object -Last N` даёт «Exited with code 1» при успехе

**Симптом.** `astro build` печатает `Complete!`, а харнесс рапортует ненулевой код.

**Причина.** Обрезка потока вывода PowerShell ломает код возврата пайплайна.

**Фикс.** Читать вывод целиком; код возврата получать через `spawnSync` в отдельном `.cjs` (в этом проекте — `run-build.cjs`).

**Урок.** Артефакт пайплайна ≠ ошибка сборки. Не «чинить» зелёную сборку.

## 20. Регекс `\w` не матчит кириллицу — проверка врала, а не код

**Симптом.** Тест «дата отформатировалась в русский формат» падает, хотя на странице всё правильно.

**Причина.** В проверке `/\\d{1,2} \\w+ 20\\d\\d/` класс `\w` — это `[A-Za-z0-9_]`. Месяц «июня» не подходит, тест красный на заведомо верном выводе.

**Фикс.** `/\\d{1,2} [а-яё]+ 20\\d\\d/`.

**Урок.** Красный тест — это утверждение о коде, а не о системе. Прежде чем «чинить реализацию», проверить саму проверку. Особенно на не-ASCII данных.

## 21. `src/content/*.json` — данные, а не артефакт

**Симптом.** После `git clean -fdx` / свежего клона сайт показывает пустой контент.

**Причина.** `src/content/` попал под игнор вместе с артефактами сборки.

**Фикс.** Файлы контента **в репозитории** — это сид и основа данных проекта. В `.gitignore` только `node_modules/`, `dist/`, `.astro/`.

**Урок.** Данные и артефакты нельзя разделять по «лежит в src». Критерий: теряет ли проект функциональность при удалении.

## 22. Путь к хранилищу нельзя жёстко привязывать к `cwd`

**Симптом.** В dev контент читается, в собранном сервере — `ENOENT` или запись в неожиданную папку.

**Причина.** `path.resolve(process.cwd(), 'src/content')` зависит от того, **откуда** запущен процесс. В dev это корень проекта, в `dist/server/entry.mjs` — может быть иначе.

**Фикс.** `resolveContentDir()`: приоритет `NLB_CONTENT_DIR` → `<cwd>/src/content` → `../../src/content` относительно модуля → первый существующий. Плюс внятная ошибка при недоступности на запись.

**Урок.** Путь к данным не должен выводиться из предположения о cwd. И запись в read-only окружении должна давать понятное сообщение, а не стек.

## 23. `src/content/` — зарезервированная директория Astro

**Симптом.** При каждой записи в хранилище dev-сервер печатает:

```
[WARN] [content] posts.json must live in a content/... collection subdirectory.
```

Сборка проходит с `BUILD_EXIT=0`, всё работает. Но предупреждение сыпется на каждый `POST`/`PUT`/`DELETE` в `/api/admin/posts` и один раз при старте.

**Причина.** `src/content/` в Astro зарезервирован под content collections. Файлы там должны лежать в подкаталоге коллекции (`src/content/<collection>/<entry>.json`). Наш `src/content/posts.json` — обычный JSON, читаемый через `fs`, а не через `getCollection`.

**Почему это не просто шум.** Сейчас безобидно. Но как только кто-то добавит content collection с коллекцией `posts`, файл станет кандидатом на автогенерацию коллекции — и данные, которые ведёт админка, окажутся под управлением генератора. Столкновение имён не даст ошибки при сборке заранее.

**Фикс (не применён — ждёт решения).** Варианты:

| Вариант | Плюс | Минус |
|---------|------|-------|
| `src/content/nlb/posts.json` | предупреждение гаснет, путь остаётся | `nlb/` ничего не значит, каша |
| `src/data/posts.json` | честно: это данные, не коллекция | правило «`src/data/` — моки исходника» придётся уточнить |
| оставить как есть | ноль правок | предупреждение на каждой записи |

При переносе править **только** `resolveContentDir()` в `src/lib/content.ts` и пути в доках. Файл переезжает вместе с данными.

**Урок.** Предупреждение сборщика, которое повторяется на каждой операции, — не «шум, привыкли». Первое же предупреждение означает, что используешь чужую директорию. Зарезервированные пути фреймворков работают неявно: конфликт проявится позже и в другом месте.

## 24. `site` в astro.config — не значение, а окружение

**Симптом.** После выката `canonical` на всех страницах указывает на `http://localhost:4321/...`, а `sitemap.xml` перечисляет те же адреса. Поисковик либо игнорирует `canonical`, либо объявляет каноническим чужой домен.

**Причина.** `site: 'http://localhost:4321'` зашит литералом в `astro.config.mjs`. Локально это правильное значение — проект ни разу не выкатывался, и других окружений не существует. Поэтому баг не проявляется **до первого деплоя**, а после деплоя требует правки отслеживаемого исходника.

**Почему это дороже, чем кажется.** Ошибка не в значении, а в способе его задания. Пока домен зашит в файл, смена домена = коммит в исходники. Такой коммит забывают. Дальше — правка исходника, ревью, релиз, и только потом выясняется, что половина сайта объявляет каноническим `localhost`, а это чужой домен, который может отдавать что угодно.

**Фикс.** `site: process.env.SITE_URL ?? 'http://localhost:4321'`. Домен задаётся окружением при выкате, исходник не трогается.

**Побочный случай, который чуть не попал в прод.** Наивное «сделаем robots.txt статическим файлом в `public/` с относительным `Sitemap: /sitemap.xml`» выглядит как избавление от хардкода. Это неверно: RFC 9309 требует **абсолютный** URL в директиве `Sitemap:`. Google относительный путь исторически прощает, но это не спецификация — и полагаться на поблажку Google на сайте с Яндексом в доле трафика нельзя. Правильно — эндпоинт `src/pages/robots.txt.ts`, который подставляет тот же `SITE_URL` в рантайме.

**Урок.** Значение окружения нельзя зашивать в исходник, даже когда оно «заведомо правильное для текущего окружения». Ошибка отложена по времени, а не устранена. Отдельно: относительный путь не решает задачу, если настоящая проблема — в другом файле. Хардкод был в `site`, а не в `robots.txt`.

## 25. `process.env` в конфиге — это build-time, а не runtime

**Симптом.** Выкатили проект: `robots.txt` отдаёт правильный домен, а `sitemap.xml` и `canonical` на всех страницах — `http://localhost:4321`. Домен «половинился»: один файл про домен знает, остальные нет.

**Причина.** `SITE_URL` читается в `astro.config.mjs`, а конфиг выполняется **один раз, при запуске `astro build`**. Всё, что выведено из `site`, уходит в `dist/` навсегда: `sitemap.xml` пишется сборщиком, `canonical` попадает в пресиренренный HTML. Рантайм-переменная, поданная контейнеру при старте, в эти файлы уже не попадает.

Исключение — `src/pages/robots.txt.ts` с `prerender = false`: он читает `process.env` при старте сервера и отдаёт правильный домен. Именно поэтому расхождение неочевидно: **один файл из трёх выглядит рабочим**, и при беглой проверке всё кажется исправленным.

**Фикс.** `SITE_URL` обязана быть в окружении **сборки**, а не только рантайма. Проверка:

```bash
SITE_URL=https://example.com npm run build
grep -c example.com dist/sitemap.xml   # > 0
grep -c localhost   dist/sitemap.xml   # 0
```

Пункт 9 в pre-flight чеклисте (`docs/AGENTS-production.md`) делает эту проверку обязательной перед каждым выкатом.

**Урок.** Переменная окружения в конфиге фреймворка — это значение времени **сборки**, даже если файл называется `.env` и читается как «в рантайме». Собирать деплой с `SITE_URL` и проверять выкат — разные вещи: без второго расхождение обнаруживается только поисковиком. И проверять надо все носители домена сразу, а не тот, который выглядит самым «настоящим»: правильно настроенный `robots.txt` здесь маскирует неправильный `sitemap.xml`.
