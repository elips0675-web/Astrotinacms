0. ОБЩИЙ ПРИНЦИП РАБОТЫ — 5 ЭТАПОВ
--------------------------------------------------------------------------------

Каждая задача проходит 5 этапов. Этап 0 пропускать нельзя: 5 минут чтения
экономят час отладки.

Этап 0 — Чтение
  1. Прочитать `AGENTS.md` и `docs/AGENTS-porting.md` (если трогаешь публичную
     часть) и `docs/AGENTS-pitfalls.md` (всегда).
  2. Найти релевантные файлы (grep/glob).
  3. Понять data flow: кто пишет, кто читает, кто рендерит.
  4. Проверить, что уже сделано: `grep -rn "MOCK_" src/pages/admin/`.

Этап 1 — Планирование
  1. Определить границы: что входит, что НЕ входит.
  2. Выбрать архитектурное решение (1–2 предложения).
  3. Составить список файлов.
  4. Спросить пользователя, если архитектура неоднозначна. Не угадывать.

Этап 2 — Реализация
  1. Сначала типы (TS strict, без `any`).
  2. Потом data layer (`src/lib/content.ts`, API).
  3. Потом UI.
  4. Каждый коммит — одна атомарная единица.
  5. Conventional Commits: feat:, fix:, refactor:, test:, docs:, chore:, ci:.

Этап 3 — Тестирование
  1. Прогнать скрипты, затронутые изменением (см. ИНВЕНТАРЬ-ТЕСТОВ.md).
  2. Проверить edge cases: пустые данные, ошибки, лимиты.
  3. `node %TEMP%\opencode\run-build.cjs` → BUILD_EXIT=0.

Этап 4 — Верификация
  1. Старые проверки не упали.
  2. Браузер: консоль без ошибок, Network-статусы верные.
  3. Dev И build (для правок astro.config.mjs — обязательно оба).
  4. Обновить документацию в этом же коммите.

1. ПРОМТ: ПОЛНЫЙ ФУНКЦИОНАЛЬНЫЙ АУДИТ
--------------------------------------------------------------------------------

Проведи полный функциональный аудит проекта D:\Astro tinacms.

Стек: Astro 4.16.19 (output: 'hybrid') + React 18 островами + Tailwind v3,
хранилище контента — JSON на диске, API — Astro APIRoute.
Контекст: test/Для анализа.txt и test/СВОДКА.md.

Что проверить, в этом порядке приоритета:
  1. ЗАМКНУТЫЙ ЦИКЛ КОНТЕНТА — создание в /admin/content/new → /api/admin/posts
     → src/content/posts.json → /all-news → /news/<id>. Главный вопрос: правка
     видна на сайте БЕЗ пересборки?
  2. ЧЕРНОВИКИ — скрыты с сайта И отдают 404 (а не только скрыты)?
  3. ВАЛИДАЦИЯ API — пустой заголовок, битый JSON, DELETE без id, DELETE
     несуществующего, PUT без id. Проверь, что отсутствие параметра
     проверяется ДО Number(), а не после.
  4. АДМИНКА — какие разделы читают MOCK_* и ничего не сохраняют?
  5. РОУТИНГ — все страницы из getStaticPaths реально попадают в сборку?
     Есть ли ссылки на id, которых нет ни в одном getStaticPaths?
  6. ПУБЛИЧНЫЕ СТРАНИЦЫ — остров гидратирован? Слайдер на /services выглядит
     как в исходнике (точки 28×10px, радиус 6px, градиент; стрелки скрыты)?
  7. ХРАНИЛИЩЕ — атомарность записи, поведение при read-only FS, конкурентная
     запись, разрешение пути (NLB_CONTENT_DIR).
  8. БЕЗОПАСНОСТЬ — /admin и /api/admin/* открыты. Оцени риск и предложи
     минимальный порядок внедрения защиты.

Формат ответа: таблица «проверка / статус (✅/❌/⚠️/❓) / файл:строка /
риск / что делать». Без правок кода.

4. ПРОМТ: НАПИСАНИЕ ТЕСТОВ (этап 6 бэклога)
--------------------------------------------------------------------------------

Настрой Vitest и Playwright в D:\Astro tinacms. Сейчас автотестов нет.

Часть A — инфраструктура
  1. Установи vitest, @vitest/coverage-v8, playwright/@playwright/test.
     npm install на этой машине требует флагов:
     --no-audit --no-fund --legacy-peer-deps --ignore-scripts
  2. vitest.config.ts: среда node для src/lib и API, jsdom для компонентов
     админки. include: src/**/*.{test,spec}.{ts,tsx}.
  3. npm run test и npm run test:e2e в package.json.
  4. Playwright: webServer поднимает `npm run dev` на :4321, baseURL
     http://localhost:4321, trace on-first-retry.

Часть B — юнит (Vitest)
  Обязательный минимум:
  - src/lib/content.ts: formatDate (ISO → русский формат, и «как есть» для
    готовой строки), toPublicNews (body = content || excerpt),
    readPublished (фильтр visible + status), upsert (новый id, дефолт
    visible: true), remove.
  - resolveContentDir: приоритет NLB_CONTENT_DIR → cwd → путь от модуля.
  - Валидация API-роута: пустой заголовок, битый JSON, отсутствие id.

Часть C — E2E (Playwright), критические флоу
  - Замкнутый цикл: /admin/content/new → заполнить → Опубликовать →
    запись видна на /all-news → открывается /news/<id> с полным текстом →
    удалить → пропала.
  - Черновик: не виден на /all-news, /news/<id> отдаёт 404.
  - Черновик виден в /admin/content (админ видит, сайт — нет).
  - 404 на несуществующем маршруте.
  - Гидратация острова: у <astro-island> нет атрибута ssr на /services.

Часть D — обязательное требование
  E2E, создающие контент, обязаны чистить за собой: teardown возвращает
  src/content/posts.json к 19 строкам. Проверка после прогона:
  node -e "console.log(require('./src/content/posts.json').length)"  → 19

Ловушки (см. docs/AGENTS-pitfalls.md):
  - Не проверяй дату регексом с \w — месяц кириллицей не матчится.
  - Мок контекста/хука обязан возвращать стабильный объект, иначе эффект
    зациклится и прогон подвесится целиком.
  - Number(null) === 0 — тест на «нет id» обязан ловить 400, а не 404.

Формат ответа: сначала список файлов, затем код, затем фактический вывод
прогона (`npm run test` и `npm run test:e2e`) с числами тестов.

5. ПРОМТ: РАЗБОР БАГА
--------------------------------------------------------------------------------

Симптом: <что наблюдается>
Ошибка:  <точный текст из консоли или терминала>
Где:      <маршрут или файл>

Прежде чем чинить, проверь три вещи — иначе рискуешь чинить не то:
  1. Это баг кода или баг проверки? Регекс \w не матчит кириллицу —
     проверка может врать на заведомо верном выводе (pitfall 20).
  2. Не следствие ли это устаревшего дев-сервера? Процесс на :4321 мог
     пережить правку astro.config.mjs и отдавать старый граф (pitfall 17).
  3. Не следствие ли это транзиентной ошибки конфига? Перечитай файл перед
     выводами (pitfall 16).

Потом: минимальный фикс → прогон затронутых скриптов → новый пункт в
docs/AGENTS-pitfalls.md в формате «симптом → причина → фикс → урок».

6. ПРОМТ: ПОЧИНКА 30 СЛОМАННЫХ СТРАНИЦ
--------------------------------------------------------------------------------

Симптом: страницы /services и динамические роуты падают с
«exports is not defined» в dev. В build при этом всё зелёное.

Подсказка (не решение, а направление): react-slick — CJS-пакет. Флаг
ssr.noExternal чинит build и ЛОМАЕТ dev. Это не взаимозаменяемые настройки,
поэтому «починить одно и считать, что другое тоже починено» здесь не работает.

Требования:
  - Не возвращать ssr.noExternal в astro.config.mjs.
  - Решение должно работать и в dev, и в build.
  - Публичные компоненты не трогать сверх необходимого.

Проверка:
  node %TEMP%\opencode\smoke.mjs     → 69/69
  node %TEMP%\opencode\probe-slick.mjs   → слайдер рендерится
  node %TEMP%\opencode\probe-slick2.mjs  → точки и стрелки как в исходнике

7. ПРОМТ: ВНЕДРЕНИЕ АВТОРИЗАЦИИ
--------------------------------------------------------------------------------

В D:\Astro tinacms добавь авторизацию на /admin и /api/admin/*.
Сейчас оба открыты любому посетителю.

Требования:
  1. Сессия — httpOnly + SameSite=Lax + Secure (в проде) cookie.
     Не localStorage, не sessionStorage.
  2. Пароль — argon2id или bcrypt. Не SHA-256, не MD5.
  3. Проверка прав на КАЖДЫЙ запрос /api/admin/*, а не только на страницах.
  4. Fail closed: нет токена → 401, есть токен не-админа → 403.
  5. Сравнение — timing-safe.
  6. Выход из системы инвалидирует сессию на сервере.
  7. Открытый редирект запрещён: принимать только пути внутри /admin.
  8. Публичный контент (GET /all-news, /news/<id>) остаётся без прав.

Побочный эффект, который надо обработать: после внедрения /admin начнёт
отдавать 401/302. Скрипты smoke.mjs и test-loop.mjs ходят в /admin без
токена — их надо либо научить логиниться, либо разделить на публичные и
админские. Не молча оставить красным.

Проверка:
  node %TEMP%\opencode\smoke.mjs    → публичные 200, /admin 401/302
  тест «без токена → 401 ДО логики хендлера»

Оцени промт по шкале 0–10 и перепиши его.

Критерии:
  Конкретность цели   — «улучшить сайт» (0) … «точки 28×10px, радиус 6px» (10)
  Ограничения        — нет (0) … «только механические правки, перечислить
                       исключения» (10)
  Команда проверки   — нет (0) … «compare-src.mjs → только механические
                       отличия; smoke.mjs → 69/69» (10)
  Границы             — нет (0) … «файлы: A, B, C. Не трогать: D, E.
                       Причина ограничения — pitfall 9» (10)
  Однозначность       — требует уточнений (0) … ясно с первого прочтения (10)

Правила улучшения:
  1. Убрать «сделай хорошо / аккуратно / как надо» — они не несут информации.
  2. Добавить измеримое ожидание.
  3. Добавить команду проверки.
  4. Назвать границы файлов.
  5. Ссылаться на pitfall, если ограничение из опыта.

Пример:
  Было:  «Почини админку»
  Стало: «Раздел /admin/services читает MOCK_SERVICES и ничего не сохраняет.
          Перевести на src/lib/content.ts по паттерну постов. Результат:
          форма сохраняет, изменение видно на /services без пересборки.
          Проверка: grep -rn MOCK_ src/pages/admin/ пустеет на этой строке;
          создать услугу через UI → появляется на сайте. Итог: BUILD_EXIT=0,
