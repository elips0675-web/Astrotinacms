ЭТАП 0 — РАЗВЕДКА И РЕШЕНИЯ ПО АРХИТЕКТУРЕ
--------------------------------------------------------------------------------

Задача
  Понять исходник D:\nlb-studio6-main и выбрать способ переноса.

Решения (каждое — с обоснованием, не «по умолчанию»)
  • Порт как React SSR + острова, а не переписывание в .astro.
    Причина: гарантирует идентичную разметку. Главное требование — паритет.
  • Tailwind v3, не v4. В исходнике нет v4-синтаксиса.
  • react-router-dom заменён шимом, алиасом в astro.config.mjs.
    Причина: Astro использует файловый роутинг; нативный react-router в
    острове упирается в отсутствие SSR-контекста роутера.
  • Роутер-контекст живёт внутри острова (withRouter), а не в .astro.
    Причина: React-контекст не пересекает границу островов.
  • Админка — серверный Astro + vanilla JS, без React-островов.
    Причина: там нет сложного состояния, React-островы были бы лишним весом.
  • TinaCMS НЕ используется. Причина: peer-конфликт (пункт 9 бэклога).
  • page-templates/ не портирован — мёртвый код в исходнике.

Проверено
  Проект собирается, dev-сервер поднимается.

Что было
  Форма имела method="post" без action и без бэкенда. Внешне выглядела
  как рабочая админка, по факту ничего не сохраняла. project output был

Сделано
  • output: 'hybrid' + @astrojs/node (mode: 'standalone').
  • src/lib/content.ts — хранилище:
      readAll / readPublished / upsert / remove / toPublicNews / formatDate /
      resolveContentDir
      Атомарная запись: tmp + fs.rename (падение посреди записи не оставит
      битый JSON).
      resolveContentDir: NLB_CONTENT_DIR → <cwd>/src/content →
      ../../src/content от модуля → первый существующий. Путь не выводится
      из предположения о cwd.
      Чтение через fs, а не import: импорт JSON проходит через кэш Vite и
      правка из админки не была бы видна без рестарта.
  • src/pages/api/admin/posts.ts — CRUD с валидацией на сервере:
      GET / POST / PUT / DELETE?id=
  • src/components/ContentEditor.astro — редактор переведён на fetch к API.
      Есть id: #publish-post, #save-draft, #editor-toast, data-post-id.
  • src/pages/admin/content/index.astro — список на SSR, поиск, удаление,
      data-post-id, data-delete-post, #post-search.
  • src/pages/all-news.astro и src/pages/news/[id].astro —
      export const prerender = false, читают хранилище на каждый запрос.
  • src/content/posts.json — 19 записей: 14 visible: true (новости сайта) +
    5 visible: false (демо админки). Поле visible нужно, иначе демо-английские
    посты попали бы в ленту и изменили вид сайта.
  • Публичный DTO: toPublicNews() маппит ContentItem → PublicNews, чтобы
      внутренние поля не протекали на публичные страницы.

Замкнутый цикл — проверен в реальном браузере
  Заполнить форму → «Опубликовать» → запись создана → видна на /all-news →
  /news/<id> рендерит полный текст. После проверки запись удалена,
  хранилище возвращено к сиду.

Найдено и починено 2 настоящих бага
  1. Number(null) === 0. DELETE без ?id= проходил валидацию и отдавал
     404 «Запись не найдена» вместо 400 «Не передан id». Отсутствие
     параметра проверяется ДО Number().
  2. Страница новости рендерила только description, теряя content из
     админки. Поле content молча пропадало на пути запись → чтение → рендер.
     Добавлено PublicNews.body = content || excerpt; рендер item.body ||
     item.description. У сидированных новостей content === description,
     поэтому внешний вид не изменился.

  .env.example, где было написано «подставляется в рантайме».

  Реальный сценарий поломки: образ собирают без SITE_URL, а переменную
  передают контейнеру при старте. Тогда robots.txt (prerender = false, читает
  env при старте сервера) отдаёт правильный домен, а sitemap.xml и canonical —
  нет, потому что они запечены в dist/ навсегда. Домен «половинится», причём
  правильно настроенный robots.txt маскирует неправильный sitemap.xml.

  находка.

Замечание, которое стоит учесть по существу
  Файл предлагает не писать E2E-тест записи контента на том основании, что
  «локально он будет зелёным всегда, поэтому ценность ограничена». Это
  рассуждение опасно: тест, проверяющий что правка видна на сайте без
  пересборки, локально зелёный и в этом его смысл — он ловит именно то
  расхождение, из-за которого форма выглядит рабочей, а контент не меняется.
  То, что тест проходит до решения вопроса с правами на том, не делает его
  бесполезным, а переносит вопрос: он проверяет фикс, а не окружение.
